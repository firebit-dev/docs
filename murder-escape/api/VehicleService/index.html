VehicleService

This item only works when running on the server. Serverdormant

Handles vehicle spawning, despawning, and player lifecycle.

Responsibilities

This service owns the one vehicle per player invariant and is the entry point every other server system uses. It holds a player → car Model map and delegates all per-vehicle behaviour to a Vehicle instance looked up from that model via Vehicle.getCar. That indirection is why nearly every method here is the same three-step shape: resolve the player's car, resolve its Vehicle wrapper, forward the call.

Physics lives on the driver's client (see VehicleController); this side owns existence, seat authority, attachments and stats.

Occupancy bridge

VehicleService._connectOccupantSignal is the seam between the two realms. A Vehicle fires occupiedSignal when someone takes or leaves the driver's seat; this service turns that into a VEHICLE_START_CONTROL dispatch to that client (which starts or stops its physics loop) and mirrors the state onto the character's InVehicle attribute so other systems can read it without asking.

Gated by FeatureFlags.Vehicle — disabled by default; per-project forks enable it deliberately. With the flag off neither init nor start runs, so the remote handlers are never registered and no vehicle can be spawned from the client — but the direct API below is still callable by server code.

spawnVehicle​

</>
VehicleService.spawnVehicle(
player: Player--

Owner of the new vehicle

) → Model?--

The spawned car, or nil

Spawns a vehicle for player and returns its model, or nil if it could not be placed.

Refused outright in the lobby (PlaceUtility.isLobby) and while the player's one-second debounce is active. Any existing vehicle is despawned first, which is what enforces one vehicle per player — this is a replace, not an add.

Placement itself is decided by Vehicle.new, which re-runs the same ground and clearance checks the client did before asking; a nil from there means no legal spot and is returned as-is.

On success it starts the vehicle's idle despawn timer, wires the occupancy bridge, records an analytics event, and fires VehicleSpawned.

despawnVehicle​

</>
VehicleService.despawnVehicle(player: Player) → ()

Removes the player's vehicle and fires VehicleDespawned. No-ops if they have none.

Prefers the Vehicle wrapper's Destroy so the despawn timer is cancelled and seated characters have their collision restored; falls back to destroying the bare model if the wrapper is somehow missing from the cache.

</>
VehicleService.equipAttachment(

Key into VehicleAttachmentData

) → boolean--

Whether the attachment is now equipped

Equips an attachment onto the player's vehicle.

Slots hold one attachment each: whatever currently occupies config.attachmentType is removed first, so equipping is idempotent and swapping needs no explicit unequip.

Returns false for an unknown attachment name, a player with no vehicle, or a failed attach (bad slot, model without a PrimaryPart).

setSpeedMultiplier​

</>
VehicleService.setSpeedMultiplier(
player: Player,
multiplier: number--

0..1

) → ()

Scales the player's vehicle's top speed. The value is written to the car's SpeedMultiplier attribute and read by the driving client each frame, so it takes effect immediately without a remote.

Clamped to 0..1 by Vehicle:SetSpeedMultiplier — this can only ever slow a vehicle down, and 0 is a full stop.

Cuts the player's vehicle to zero speed by setting its multiplier to 0. The multiplier stays at 0 until something raises it — taking the driver's seat resets it to 1.

</>
VehicleService.logDistanceDriven(

) → ()

Credits distance driven to the player's profile and records it in analytics.

Called from the VEHICLE_LOG_DISTANCE handler when a driver dismounts, so the value originates on the client. It is capped at what a car could cover since the last credit (or the player's first spawn); a player who never spawned a vehicle this session is credited nothing.

ProfileService is required lazily inside the function to avoid a require-time cycle between the two services.
