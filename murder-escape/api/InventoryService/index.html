InventoryService

This item only works when running on the server. Server

Handles player inventory management, including validating, retrieving, adding, and removing items.

The inventory is a flat array of [ItemRecord] stored at profile.metadata.data.inventory. Every mutation goes through ProfileService.update with the "inventory" key so the player's replica stays in sync — there is no other replication path.

Slot allocation

A record lives in exactly one of two places, and which one is encoded by which index field is non-nil:

  • Hotbar — slotIndex set (1 .. InventoryData.MAX_HOTBAR_SLOTS), bagIndex nil.
  • Bag — bagIndex set (1 .. n), slotIndex nil.

Callers must never set both. The move helpers (InventoryService.moveToHotbar, InventoryService.moveToInventory) keep the invariant by unsetting the opposite field after a successful set, and roll back to the prior state when any step of a swap fails.

slotIndex uniqueness is enforced — InventoryService.setItemSlot refuses a slot that InventoryService.isSlotTaken reports occupied. bagIndex uniqueness is not enforced by InventoryService.setItemBagIndex; it relies on InventoryService.getNextBagIndex always handing out highest existing + 1. Because that allocator never reuses freed indexes, the bag develops gaps, which are closed only by InventoryService.cleanBagIndexes.

Both compaction passes (InventoryService.cleanSlotIndexes and InventoryService.cleanBagIndexes) work by sorting the inventory array itself — records with no index sort last via math.huge — and then rewriting each indexed record's index to its array position. The physical array order therefore is the compacted order, and the two passes reorder the same array against different keys.

Stacking

Quantity is capped per record at InventoryData.MAX_STACK. InventoryService.addQuantityToItemId tops up the first non-full record for that item and then spills the remainder into freshly created records. Passing props bypasses stacking entirely and always mints a new record, since props make records non-interchangeable.

Persistence

FeatureFlags.SaveInventory is on in this game, so the inventory and inventory_equipped survive a rejoin. With it off (core's default), ProfileService empties both at load and inventories are session-only. In Studio, InventoryService.seedDefaultItems backfills an empty inventory that won't be saved with STUDIO_DEFAULT_ITEMS, so the backpack has something to test against.

Adds a quantity of an item, stacking into existing records and spilling into new ones as needed.

Without props: tops up the first record for that item that is below InventoryData.MAX_STACK, then mints additional full-or-partial records until the requested quantity is placed. With props: skips stacking and always creates exactly one new record, because prop-bearing records are not interchangeable with plain ones.

Each new record is placed in the first free hotbar slot (InventoryService.getFirstAvailableSlot); if the hotbar is full it gets a bagIndex from InventoryService.getNextBagIndex instead. Every new record is dispatched to the client as ITEM_SHOP_ITEM_ADD.

Allocates the next bag index as highest existing bagIndex + 1, or 1 when the bag is empty or no profile is loaded.

cleanSlotIndexes​

</>
InventoryService.cleanSlotIndexes(
player: Player--

inventory owner

) → boolean--

false only when no profile is loaded

Renumbers hotbar slots to be sequential from 1, closing any gaps.

Works by sorting the inventory array by slotIndex ascending — bag records sort last because their nil index is treated as math.huge — so the hotbar records land in array positions 1 .. n and each is then assigned its own array position as its new slotIndex. Bag records are skipped and keep their bagIndex untouched.

cleanBagIndexes​

</>
InventoryService.cleanBagIndexes(
player: Player--

inventory owner

) → boolean--

false only when no profile is loaded

Cleans up bag indexes to be sequential starting from 1 — closes any gaps.

The mirror of InventoryService.cleanSlotIndexes, sorting on bagIndex instead so bag records occupy array positions 1 .. n and take those positions as their new indexes. Hotbar records sort last and are skipped.

This is the only thing that reclaims the gaps left by InventoryService.getNextBagIndex's monotonic allocation, so it should run after any batch of bag removals.

moveToHotbar​

</>
InventoryService.moveToHotbar(
player: Player,--

inventory owner

payload: Actions.InventoryMoveToHotbarPayload--

recordId and target slotIndex

) → boolean

Moves an item from the bag into a specific hotbar slot. Backs the drag-drop flow from the client.

Validates the slot is in range and the record is genuinely owned, then:

  1. Clears the record's current slot, if it already sat in the hotbar.
  2. If the target slot is occupied, evicts the sitting item to the bag by clearing its slot and giving it a fresh InventoryService.getNextBagIndex.
  3. Places the moving record into the target slot and clears its bagIndex.

Every step is rolled back on failure — the evicted item is restored to the slot it was pushed out of — so a partial move never leaves two items sharing a slot or an item holding both indexes.

swapSlots​

</>
InventoryService.swapSlots(
player: Player,--

inventory owner

payload: Actions.HotbarSwapSlotsPayload--

fromSlotIndex and toSlotIndex

) → boolean

Swaps the occupants of two hotbar slots.

Both indexes must be in range and distinct, and the source slot must hold an item; the destination may be empty, in which case this is a plain move. The destination item is unslotted first so the source can claim its slot without tripping the InventoryService.setItemSlot occupancy check, then it takes the vacated source slot. If that final placement fails, both records are restored to their original slots.

Only slotIndex is touched — neither item gains a bagIndex.

swapBagSlots​

</>
InventoryService.swapBagSlots(
player: Player,--

inventory owner

payload: Actions.InventorySwapBagSlotsPayload--

fromRecordId and toRecordId

) → boolean

Swap two bag items by their recordIds. Each item must already have a bagIndex (i.e. live in the bag, not the hotbar). The bagIndexes are swapped in place — no slotIndex is touched, so neither item enters the hotbar as a side effect.

Rejects the swap when the two ids are equal, when either record is missing, when either record currently sits in the hotbar (slotIndex set), or when either lacks a bagIndex. Because it is a pure exchange of two existing indexes it cannot create a collision and needs no rollback path.

sellItem​

</>
InventoryService.sellItem(

Sells a quantity from a single record and credits the player.

Independent of InventoryService.processSellTransaction — this path applies BoostData.modifyValueWithBoosts and then the record's own props to the base resale value, and credits exactly once. Unlike the sell-all path it does compensate on failure, re-adding the sold quantity when the coin credit fails.
