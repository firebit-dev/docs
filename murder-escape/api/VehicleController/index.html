VehicleController

This item only works when running on the client. Clientdormant

Handles client-side vehicle physics (Ackermann steering, throttle, submarine mode), input, and distance tracking.

Why the physics is client-side

The server owns existence — spawning, despawning, seat authority, and the distance stat — while the driver's own client owns motion. The client that occupies the DriverSeat has network ownership of the assembly anyway, so simulating there is both authoritative in practice and latency-free. The server is told only the outcome (VEHICLE_LOG_DISTANCE on dismount).

Singleton, not per-vehicle

This is a module-level singleton holding one car at a time — the vehicle this client may drive. VehicleController.setupCar overwrites that reference wholesale. Other players' vehicles are not tracked at all; their enter prompt is simply destroyed so they cannot be boarded.

Two states

A vehicle is either driving or submarine, switched by VehicleController.setState off the character's Swimming attribute. The two modes drive completely different mechanisms and only one is ever live:

  • driving — four CylindricalConstraint wheel motors plus two front spring attachments used as steering knuckles. Torque on, flight constraints off.
  • submarine — an AlignOrientation/AlignPosition/VectorForce rig that flies the chassis; the camera becomes the control surface. Torque zeroed, wheel motors idle.

Update pipeline

VehicleController.startControl binds VehicleController.update to Heartbeat. Each frame update handles the shared concerns — idle detection, station keeping, and cutting power when the seat is empty — then delegates to VehicleController.updateCar or VehicleController.updateSubmarine.

Steering geometry

Wheelbase and track width are measured from the actual constraint attachments in VehicleController.setupCar using Magnitude, so they are rotation-invariant and a re-authored car model needs no code change.

Gated by FeatureFlags.Vehicle — disabled by default; per-project forks enable it deliberately. Both VehicleController.init and VehicleController.start return immediately when the flag is off, so nothing is tagged, bound or subscribed.

Functions​

init​

</>
VehicleController.init() → ()

Bootstrap hook. Adopts every existing Vehicle-tagged model and subscribes to later additions.

No-ops entirely when the Vehicle feature flag is off.

start​

</>
VehicleController.start() → ()

Bootstrap hook. Subscribes to VEHICLE_START_CONTROL, the action the server dispatches when this player takes or leaves the driver's seat. Taking control hides the enter prompt and starts the physics loop; releasing it does the reverse.

No-ops entirely when the Vehicle feature flag is off.

setupCar​

</>
VehicleController.setupCar(
car: Model--

The vehicle model to adopt

) → ()

Adopts car as the vehicle this client controls: resolves every instance the physics loop needs, measures the steering geometry, resets all motion state, and wires the lifetime listeners.

Expects a specific model layout — DriverSeat, Chasis/Platform/Engine, the four Cylindrical* wheel motors on the engine, SpringAttachmentF* on the platform, and a Flight folder holding the submarine constraints. Every lookup is a WaitForChild, so a model missing any of these hangs here rather than erroring.

Steering geometry is derived from the live attachment positions rather than hard-coded: track width from the two front spring attachments, wheelbase from front-left to rear-left. Both use Magnitude, so they hold regardless of how the model is oriented when this runs.

The car is un-anchored at the end — models are spawned anchored so they cannot drift before their constraints are configured.

The initial state is chosen from the character's Swimming attribute, and a listener keeps it in sync afterwards. Transitions out of water deliberately wait 0.4s (guarded by switchingState) so the vehicle does not snap back to driving mode while it is still breaching the surface.

Yields on the WaitForChild calls.

setState​

</>
VehicleController.setState(
state: VehicleTypes.CarState--

"driving" or "submarine"

) → ()

Switches the vehicle between driving and submarine. No-ops if already in that state.

The two modes are mutually exclusive by construction: the four flight constraints are enabled only for submarine, and wheel MotorMaxTorque is set to the full torque for driving and to zero otherwise. Zeroing torque rather than disabling the constraints leaves the wheels free-spinning, which is what lets a submarine coast rather than dragging its brakes.

Before switching, the target orientation is seeded from the vehicle's current world orientation so a submarine does not snap to an arbitrary heading the instant it enters the water.

updateSubPhysics​

</>
VehicleController.updateSubPhysics() → ()

Recomputes the submarine rig from the vehicle's current mass.

subForce is exactly mass * gravity — the force the anti-gravity VectorForce must apply to hold the vehicle neutrally buoyant, so vertical control becomes a signed offset around zero rather than a fight against gravity. The station-keeping AlignPosition gets a quarter of that, deliberately weak so it holds position without fighting the movement force.

While in submarine mode it also re-anchors the hold position to where the vehicle actually is, so the rig never tries to drag it back to a stale point.

updateTorque​

</>
VehicleController.updateTorque() → ()

Recomputes wheel torque from the vehicle's mass and applies it to the seat and all four motors. Re-runs whenever the platform's AssemblyMass changes — that is, whenever a passenger boards or leaves — so a loaded vehicle does not become sluggish.

Torque is MAX_SPEED * mass * 1.3: sizing torque against mass keeps acceleration roughly constant regardless of load, and the 1.3 is headroom for slopes. Each occupant additionally adds a flat 100 to the mass estimate, because character assemblies are not part of the vehicle's AssemblyMass.

Always calls VehicleController.updateSubPhysics first — which is also what re-reads the true assembly mass — then returns early unless the state is driving, since torque means nothing in submarine mode.

startControl​

</>
VehicleController.startControl() → ()

Takes control of the vehicle: binds the physics loop to Heartbeat, refreshes torque, raises ClientState.inVehicle, reconfigures the camera for driving (classic mode, wide zoom range, subject back on the humanoid) and plays the seatbelt SFX.

It also binds a sink action over the gameplay inputs that would otherwise fire while driving — left click, E, R, G and the equivalent gamepad buttons. Right mouse button is deliberately not sunk, because that is camera orbit.

Called from the VEHICLE_START_CONTROL subscription, not directly.

stopControl​

</>
VehicleController.stopControl() → ()

Releases control: zeroes every throttle and steering input, holds all four wheels at zero angular velocity with full torque (so the vehicle brakes and stays put rather than rolling away driverless), clears ClientState.inVehicle, and unbinds the input sink.

Finally it reports the distance travelled to the server via VEHICLE_LOG_DISTANCE and resets the counter — dismounting is the only time the odometer is flushed, so a client that never dismounts never banks the stat.

Called both from the VEHICLE_START_CONTROL subscription and from the car's Destroying handler.

updateCar​

</>
VehicleController.updateCar(
deltaTime: number--

Frame delta from Heartbeat

) → ()

One frame of car physics. Called by VehicleController.update while the state is driving.

Steering. The seat's SteerFloat is scaled to MAX_STEER_ANGLE and approached exponentially rather than snapped. The approach rate itself scales with speed (8 at idle up to 38 at full throttle), so parking manoeuvres feel weighty while highway corrections feel sharp. Both front spring attachments are then oriented to the resulting angle — this is the Ackermann knuckle rotation; the wheels themselves are driven separately below.

Throttle. ThrottleFloat is approached at THROTTLE_ACCELERATION and clamped to ±1, then multiplied by MAX_SPEED and the car's SpeedMultiplier attribute (set by the server from the vehicle's upgrades). Below 10% input the throttle bleeds toward zero, which is the engine-braking feel — releasing the key coasts to a stop instead of freewheeling.

Differential. Rather than computing true Ackermann per-wheel speeds, the inner wheels are simply slowed proportionally to steering lock (up to 60% at full lock). The resulting speed difference across the axle produces a yaw moment that helps the car rotate, which is cheaper and more forgiving than geometric Ackermann on Roblox's constraint solver. Right-side wheels take the negated speed because they face the opposite way.

Odometer. Per-frame displacement is accumulated, ignoring sub-0.1-stud deltas so physics jitter on a parked car does not inflate the total.

updateSubmarine​

</>
VehicleController.updateSubmarine(
deltaTime: number--

Frame delta from Heartbeat

) → ()

One frame of submarine physics. Called by VehicleController.update while the state is submarine.

Underwater the camera is the control surface. Steering input yaws the camera (lerped, not snapped), the vehicle's AlignOrientation then chases the camera's heading, and the camera's pitch — offset by THROTTLE_VERTICAL_DEGREE_OFFSET and normalized against THROTTLE_MAX_VERTICAL_DEGREE — becomes the dive/climb command. Looking down while accelerating dives; looking up climbs. Vertical speed is scaled by throttle magnitude, so pointing the camera down while stationary does nothing.

Throttle and steering both ease toward their goals and bleed back to zero below 10% input, the same engine-braking feel as the car. All submarine speeds are additionally scaled by SUBMARINE_SPEED_DAMPENING so the vehicle feels heavier in water than on land.

Two forces do the work: subMovementForce drives lateral and forward motion in the vehicle's own frame, and subAntiGravity carries the neutral-buoyancy baseline (mass * gravity) plus the vertical command on top. Because vertical control is an offset around neutral buoyancy, releasing the controls leaves the vehicle hovering rather than sinking.

update​

</>
VehicleController.update(
deltaTime: number--

Frame delta from Heartbeat

) → ()

Per-frame driver bound to Heartbeat by VehicleController.startControl. Handles what is common to both modes, then dispatches to VehicleController.updateCar or VehicleController.updateSubmarine.

Idle station-keeping. After CAR_IDLE_TIME with no input, a submarine engages its AlignPosition and re-anchors the hold point every 0.2s. That is what stops a released submarine from drifting with residual velocity; a car needs no equivalent because friction handles it.

Empty seat. If nobody is in the driver's seat, throttle is zeroed and all four wheels are held at zero velocity with full torque, and the frame ends there — an unoccupied vehicle brakes rather than coasting. This is a safety net for the window between the occupant leaving and VehicleController.stopControl running.

carLookAt​

</>
VehicleController.carLookAt(
position: Vector3--

World point to face

) → ()

Rotates the vehicle to face position over a one-second eased tween, keeping it level — the target is flattened onto the vehicle's own Y plane, so this only ever changes yaw.

Implemented by tweening a scratch CFrameValue and piping its Changed into PivotTo, since models cannot be tweened directly. All three temporaries are cleaned up afterwards.

Yields until the tween completes.

isLookingInDirectionOfPosition​

</>
VehicleController.isLookingInDirectionOfPosition(
position: Vector3--

World point to test against

) → boolean

Whether the vehicle is roughly pointed at position. Both the vehicle's look vector and the direction to the target are flattened to the horizontal plane, so pitch is ignored; the test is dot > LOOK_ANGLE (0.95), about an 18° cone.

setCarAnchoring​

</>
VehicleController.setCarAnchoring(
state: boolean--

true to anchor

) → ()

Anchors or un-anchors the vehicle by toggling Anchored on the driver's seat, which is the assembly's root — anchoring the seat freezes the whole vehicle. Used to pin a vehicle in place for scripted moments.

spawn​

</>
VehicleController.spawn() → ()

Toggle handler for the spawn button: despawns the current vehicle if one is live, otherwise finds a legal spot and asks the server to spawn one. Debounced, so a double-tap cannot fire two requests.

Placement is resolved entirely client-side before the request goes out, in two steps:

  1. Ground find. A point SPAWN_DISTANCE studs in front of the player is raycast straight down (from 10 studs up, 100 studs deep) to find the floor. No floor means no spawn — this is what stops a vehicle appearing over a ledge or above water.
  2. Clearance check. A temporary invisible part the size of the car model's bounding box is placed at the resolved spot and GetPartsInPart is run against it. Any hit aborts.

Both queries filter against the same list of Spawner- and Water-tagged instances, so spawn pads and water do not count as obstructions. The car is dropped 2 studs above the floor hit and raised by half its own height, keeping its original yaw.

The server re-validates; this check exists to give immediate feedback and to avoid spamming rejected requests.
