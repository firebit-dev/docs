OrderedDB

This item only works when running on the server. Server

Class that manages a connection to an ordered datastore.

Author: Zach (InfinityDesign)

One instance wraps one OrderedDataStore, and LeaderboardService creates one per leaderboard. On top of the raw store it adds four things:

Resilient connection. GetOrderedDataStore is wrapped in a pcall; a failure schedules OrderedDB._tryReconnect, which retries every 5 seconds indefinitely. Write methods return false while disconnected rather than erroring, so a datastore outage degrades instead of breaking callers.

Write coalescing. OrderedDB:SetValue and OrderedDB:AddToValue do not write immediately — they park the value in _lastPlayerCalls behind an UPDATE_DELAY (30s) timer. A newer call for the same user cancels the pending one, so a player earning points repeatedly costs one write rather than dozens. The deferred write re-checks that it is still the current pending call, both before and after waiting on request budget, and abandons itself if superseded.

The corresponding risk is a lost write when a player leaves mid-delay, so PlayerRemoving cancels the timer and immediately replays the pending call with skipDelay. Calls for a user who is not in the server skip the delay entirely.

Budget awareness. Every datastore call first spins until GetRequestBudgetForRequestType reports at least 3 requests available, keeping the store clear of Roblox's throttle.

Monotonic writes. OrderedDB:SetValue writes through UpdateAsync and keeps the larger of the old and new values, so a leaderboard score can only climb. forceSet switches to SetAsync for the cases that must overwrite downward. All values are floored — ordered datastores reject non-integers.

Studio

Gated on FeatureFlags.SaveInStudio (on by default). When it is off and the server is Studio, reads return random mock data (OrderedDB:GetTopValues fabricates a page seeded from the players present) and writes early-return true without touching a datastore.

) → OrderedDB

Opens a connection to the named ordered datastore, scheduling a reconnect loop if the initial connect fails.

Also installs the PlayerRemoving flush: any write still parked behind the UPDATE_DELAY timer for a departing player is cancelled and replayed immediately, so leaving the server does not drop the player's last score.

GetTopValues​

</>
OrderedDB:GetTopValues(
count: number--

how many entries to return

) → {{
key: string,
value: number
}}--

ranked entries, key is the stringified UserId

Returns the top count entries in descending order.

Pages through GetSortedAsync rather than assuming one page holds everything: it re-checks IsFinished at each page boundary and waits for request budget again before advancing, so a large count spanning several pages stays within throttle limits. Indexing is offset by page so entries are read in true rank order.

A failed GetSortedAsync warns, waits a second and retries by recursing.

In Studio without SaveInStudio, returns fabricated entries — the players currently in the server first, then random user ids — so leaderboard UI has something to render.

GetValue​

</>
OrderedDB:GetValue(
userId: number--

user to read

) → any--

Reads one user's value.

Checks the pending queue first so a value written this session is visible before it has reached the datastore. Returns nil for a user with no entry and false when the read itself failed — distinguish the two if the caller cares about the difference.

In Studio without SaveInStudio, returns a random integer.

SetValue​

</>
OrderedDB:SetValue(
userId: number,--

user to write

newValue: number,--

value to store; floored

forceSet: boolean?,--

sets the value without checking if it's higher

skipDelay: boolean?--

) → ()

Writes a user's value, coalesced behind the UPDATE_DELAY timer.

By default the write goes through UpdateAsync and keeps whichever of the old and new values is larger — a leaderboard score only climbs. Pass forceSet to use SetAsync and overwrite unconditionally, which is what LeaderboardService does when flushing a final coin balance that may have gone down.

The value is floored, since ordered datastores reject non-integers. Non-number and nil values warn and no-op. A user who is not in the server implies skipDelay.

AddToValue​

</>
OrderedDB:AddToValue(
userId: number,--

user to write

valueToAdd: number,--

delta to add; floored

skipDelay: boolean?--

write immediately instead of coalescing

) → boolean--

false on a bad value or while disconnected

Adds a delta to a user's value, coalesced behind the UPDATE_DELAY timer.

The addition happens inside UpdateAsync, so it is applied against whatever the datastore currently holds rather than a value read earlier — concurrent servers accumulate correctly.

Coalescing discards, it does not accumulate

A second AddToValue for the same user within the delay window cancels the pending one and replaces its value rather than summing the two deltas. Callers that add repeatedly should accumulate their own total and write it once, or pass skipDelay.

The delta is floored. Non-number and nil values warn and return false.

UpdateValue​

</>

userId: number,--

user to update

updateCallback: (oldValue: number?) → number--

) → boolean--

Runs an arbitrary transform against a user's stored value via UpdateAsync.

The escape hatch for logic the max-keeping OrderedDB:SetValue and the additive OrderedDB:AddToValue cannot express. Unlike those two this is not coalesced — it writes immediately, after waiting for request budget.
