AnimalPenBaseClass

dormant

Base class for every animal pen. Extends PropBaseClass; concrete pens are created through AnimalPen, which reads the pen's capacity limits out of item data and passes them down as an AnimalPenConfig.

The economy loop

A pen runs a small idle-production chain:

egg placed → incubates for `hatchTime` → hatches into a random animal
           → animal drops an item every `dropInterval`
           → drops accumulate up to `maxCapacity`
           → owner walks into the pen (or triggers the prompt) to collect

Two independent caps govern it. maxAnimals limits eggs + animals combined and is checked when an egg is placed, so a pen cannot be over-subscribed by queuing eggs. maxCapacity limits uncollected drops; once reached, production simply stops until the owner collects. That stall is the design intent — the cap is what makes collecting worth doing and what makes larger pens worth buying.

Naming

The persisted schema calls the incubating items eggs and the code calls them "products" in places; they are the same thing. Likewise drops holds both resource drops and hatched animals — an animal reaching the pen is modelled as a drop that happens to render as a walking model instead of a collectible.

Realms

The server owns all state and runs two Stepped timers (drop production and hatching), writing everything through the inherited Replica's props key. The client owns visuals: it spawns egg models with hatching progress bars, spawns animal and resource models as they appear in replicated data, and drives the collection UI. Only CollectItems and AddProduct are client-callable.

Offline progress

Because timers only run while the server does, pen state loaded from a save is replayed forward by AnimalPenBaseClass:_calculateRetroactiveDrops before the replica is created.

Gated by FeatureFlags.BaseEnabled — disabled by default; per-project forks enable it deliberately.

Creates an animal pen.

Seeds the replica with an empty pen (no eggs, no animals, no drops) at penConfig.maxCapacity, then hands off to PropBaseClass.new with the CollectItems/AddProduct client allowlist.

When restoring from a save on the server, the saved props are first replayed forward through AnimalPenBaseClass:_calculateRetroactiveDrops so the pen reflects what it would have produced while the owner was away.

Realm-specific setup afterwards:

  • Server — starts the drop timer and the hatching timer.
  • Client — starts the egg/animal/drop visualization. The owner also gets the collection UI, deferred until building finishes if the pen is still under construction.

CollectItems​

The requesting client

Client-callable entry point for emptying the pen — allow-listed in _allowedClientFunctions, so it is reached via DispatchRemoteEvent. The client calls it both from the collect prompt and automatically when the owner walks inside the pen's radius.

Verifies ownership, then clears drops, stamps lastCollectionTime, and fires Collected with the collected table — that signal is what the inventory layer credits from.

Every animal's lastDropTime is also reset to now, so collecting restarts the production cycle rather than letting a partially-elapsed interval pay out immediately afterwards.

No-ops when the pen is empty, so a spurious call costs nothing.

AddProduct​

This item only works when running on the server. Server
</>
AnimalPenBaseClass:AddProduct(
player: Player,--

The requesting client

productItemId: string,--

Item id of the egg being placed

offset: Vector2--

Pen-relative X/Z offset in studs

) → ()

Client-callable entry point for placing an egg into the pen to incubate — allow-listed in _allowedClientFunctions.

Verifies ownership, that productItemId really is an AnimalEgg, and that the offset is inside the pen. It then enforces maxAnimals against eggs plus animals combined, so a player cannot queue eggs past the pen's eventual animal limit.

On success the egg is stored with its placedAt timestamp, the egg type's hatchTime, and a random yaw; the hatching timer takes it from there. Consuming the egg from the player's inventory is the caller's responsibility.

Every rejection is a silent no-op, since the only way to reach this method is a client request that the UI should already have prevented.
