PropBaseClass

dormant

Base class for every prop that can be placed on a player's base — soil plots, animal pens, nuisances (rocks/trees/fields), town buildings, and so on. Subclasses call PropBaseClass.new with their own extra fields and inherit everything below.

Realms. The same class is constructed on both the server and the client, and new() branches into InitServer or InitClient accordingly. The two halves own different things:

  • Server owns the bounding box (a clone of the model's PrimaryPart, tagged and parented under BaseUtil.HITBOX_CONTAINER) and the authoritative [Replica]. It never builds a visual model.
  • Client owns the visual model (a clone of the prop's asset, parented to BaseUtil.PROP_CONTAINER) plus every progress bar, particle, outline and ProximityPrompt. Its bounding box is handed in by PropController.

Data flow. All shared state travels through a single Replica of class BaseUtil.PROP_REPLICA_CLASS. The server writes with Set, the client reacts with GetKeyChangedSignal. Persisted, prop-specific state lives under the props key and is reached with PropBaseClass:GetSavedProps / PropBaseClass:SetSavedProp rather than by touching the replica directly. Nothing the client does mutates state on its own — see below.

Client → server calls. The client cannot call methods on the server prop. It calls PropBaseClass:DispatchRemoteEvent, which dispatches a PROP_REMOTE_INPUT action naming a method; the server routes it through PropBaseClass:_processRemoteInput, which refuses any method not present in the prop's _allowedClientFunctions allowlist. Subclasses extend that allowlist by passing _allowedClientFunctions in the props table of new() (or by calling PropBaseClass:AllowClientFunction). Allow-listed methods receive player as their first argument and must verify ownership themselves with PropBaseClass:IsOwner — the allowlist only gates which method may be called, not by whom.

Gated by FeatureFlags.BaseEnabled — disabled by default; per-project forks enable it deliberately.

Functions​

new​

</>
PropBaseClass.new(
propData: PropData,--

Identity, placement and realm-specific handles

props: {[string]: any}?--

Extra fields for the subclass instance

) → Prop

Constructs a new Prop instance and immediately initializes the realm-specific half of it — PropBaseClass:InitServer on the server, PropBaseClass:InitClient on the client.

Subclasses call this and re-setmetatable the result onto themselves:

local self = setmetatable(
	PropBaseClass.new(propData, {
		_allowedClientFunctions = { "HarvestCrop" },
		Harvested = Signal.new(),
	}) :: any,
	Soil
) :: Soil

props is copied onto the instance verbatim with one exception: _allowedClientFunctions is merged into the base allowlist rather than replacing it, so subclasses keep CompleteBuilding for free.

GetData​

</>
PropBaseClass:GetData() → PropReplicaData

Returns the prop's current replica data, reading from whichever replica this realm owns. Both realms see the same shape and (modulo replication latency) the same values.

Errors if the prop somehow has no replica — that is a construction bug, not a recoverable state.

GetSavedProps​

</>
PropBaseClass:GetSavedProps() → {[string]: any}

Returns the prop's persisted, prop-specific state — the props table on the replica. Callable from either realm; reads whichever replica exists here.

This is the table that gets written back to the player's datastore, so subclasses keep their durable state (crops, animals, drops) inside it rather than as plain instance fields.

Errors if the prop has no replica.

IsOwner​

</>
PropBaseClass:IsOwner(
player: Player?--

Defaults to the local player on the client

) → boolean

Returns whether player owns the base this prop sits on.

The player argument is optional on the client only, where it defaults to Players.LocalPlayer. On the server, omitting it returns false — there is no sensible default, and silently answering true would defeat the ownership checks that allow-listed client-callable methods rely on.

DispatchRemoteEvent​

This item only works when running on the client. Client
</>
PropBaseClass:DispatchRemoteEvent(
eventName: string,--

Name of the server method to invoke

...: any--

Arguments forwarded after the player argument

) → ()

Asks the server to run one of this prop's methods.

Dispatches a PROP_REMOTE_INPUT action carrying propId, the method name and the varargs. The server looks the prop up and hands the action to PropBaseClass:_processRemoteInput, which rejects any name that is not in _allowedClientFunctions. 

self:DispatchRemoteEvent("HarvestCrop", cropId)

Fire-and-forget: there is no reply channel. Observe the result by watching the replica.

MoveTo​

This item only works when running on the server. Server
</>
PropBaseClass:MoveTo(
newCFrame: CFrame,--

New world origin (bottom-centre of the prop)

newPositionData: PositionData--

New plot-relative grid position

) → ()

Relocates the prop. Called by the Base class once it has validated a move request (grid snapping, plot bounds, hitbox intersection) — this method does no validation of its own.

No-ops when newPositionData is grid-equal to the prop's current position, so a rotation-only move still goes through but a redundant one does not.

Moves the server bounding box directly and publishes origin and positionData on the replica; each client then animates its own model via PropBaseClass:_localMove.

AllowClientFunction​

This item only works when running on the server. Server
</>
PropBaseClass:AllowClientFunction(
functionName: string--

Name of a method on this prop

) → ()

Adds a method name to this prop instance's client-callable allowlist at runtime. Warns and no-ops if it is already present.

Most subclasses do not need this — they pass _allowedClientFunctions in the props table of PropBaseClass.new instead, which merges into the base allowlist. Use this only when the set of callable methods depends on runtime state.

The allowlist controls what may be called, never by whom: the target method still has to check PropBaseClass:IsOwner itself.

CompleteBuilding​

This item only works when running on the server. Server
</>
PropBaseClass:CompleteBuilding(
player: Player?--

The player completing the building, if client-driven

) → ()

Finishes construction: clears buildStartTime from the persisted props and sets isBuilding to false, which the client picks up to drop the tint, fence and progress bar.

This is on the base allowlist, so the owner's client calls it over PropBaseClass:DispatchRemoteEvent when its local build timer elapses. It is also called directly by PropBaseClass:InitServer (with no player) for builds that finished while the owner was offline.

Asserts ownership when a player is supplied. A call made before the saved build window has passed finishes the build when the window ends instead.

ShowOutline​

This item only works when running on the client. Client
</>
PropBaseClass:ShowOutline(
show: boolean--

true to show, false to tear down

) → ()

Shows or hides the selection treatment on the prop — used while the prop is picked up in edit mode, and cleared when demolition starts.

Two parts, both owned by an internal Maid so hiding is a single Destroy(): the model's own Outline child (if it has one) has its parts faded in, and a bobbing, slowly rotating arrow is cloned into the Workspace above the prop. The arrow's height is recomputed every RenderStep so it tracks a prop that is being dragged.

Calling it again with true replaces the previous outline rather than stacking a second one.

GetCurrentLevelInfo​

</>
PropBaseClass:GetCurrentLevelInfo() → (
ItemTypes.PropUpgradeInfo?,
number?
)

Returns the upgrade record describing the prop's current level, plus that level number. Callable from either realm.

The upgrades list is 1-indexed from level 2 — index n describes the upgrade into level n + 1 — so the current level's record is upgrades[level - 1]. A level-1 prop therefore returns nil for the record: level 1 is the item's own base stats, not an upgrade.

GetNextLevelInfo​

</>
PropBaseClass:GetNextLevelInfo() → (
ItemTypes.PropUpgradeInfo?,
number?
)

Returns the upgrade record for the next level (upgrades[level]) and that level's number, or nil when the prop is already maxed or the item defines no upgrades. Callable from either realm.

Used both as a "can this be upgraded at all?" test and as the source of the price shown on the upgrade prompt.

ShowInfo​

This item only works when running on the client. Client
</>
PropBaseClass:ShowInfo() → ()

Attaches the persistent PropInfo billboard (item name and current level) to the model and keeps the level label in sync with the replica.

Opt-in per subclass rather than automatic — Town turns it on in its constructor, most props do not. There is no matching hide; the billboard lives until PropBaseClass:Destroy.

Destroy​

</>
PropBaseClass:Destroy() → ()

Tears the prop down on whichever realm it is called from, then fires Destroyed. Subclasses hook that signal to clean up their own state rather than overriding this method.

On the client: destroys the model, both progress bars, the outline Maid, the info billboard and the upgrade prompt, and unbinds the two RenderStep hooks registered in PropBaseClass:InitClient.

On the server: cancels the build timer/heartbeat, destroys the bounding box and the Replica, and removes the base's hitbox sub-container once it is empty.

This does not touch persisted data — removing the prop from the player's saved base is the caller's job.
