Actions

Payload types for the red action protocol, plus — in this header — a map of the protocol itself.

Actions are the only client/server channel in the game. There are no loose RemoteEvents; everything crosses the boundary as red.dispatch({ type = "NAME", payload = ... }). This module exports the payload shapes for the actions whose payloads are non-trivial. The action names themselves are plain strings at their call sites, which is why the inventory below matters.

Reading the protocol

Three call shapes appear in the codebase:

Shape Side Meaning
red.dispatch({ type = ... }) either Send. On the client it goes to the server; on the server, to one or all clients
bind("NAME", handler) server Register a handler. Handlers live in Features/*/Handler(s) modules wired up with red.useHandler(s)
red.subscribeTo("NAME", fn) client Listen. React components use the useRedAction hook, which is this plus unmount cleanup

A request/response pair usually reuses one name: the client dispatches LEVEL_GET, the bound service handler dispatches LEVEL_GET back with the answer.

Boot and player lifecycle

READY (client -> PlayerService, fires its PlayerReady signal) is dispatched by Entry.client.luau once data has loaded. PLAYER_JOINED, PLAYER_INACTIVE, PLAYER_LIVES and PLAYER_LIVES_START are server broadcasts out of PlayerService and BaseGameMode. UNLOCK_CHARACTER_MOVEMENT and PLAYERS_SPECTATE are bound in Handlers/Core and Handlers/Player.

Profile and progression

PROFILE_FETCH, PROFILE_GET, GET_PLAYER_STATS and GET_SCOREBOARD are bound in Handlers/Profile; ProfileService answers with PROFILE_GET, PROFILE_GET_LEADERBOARD_STATS, PROFILE_GET_SCOREBOARD and PROFILE_RESET. Note that bulk profile data does not travel this way — it replicates through the Profile Replica, which the client picks up in DataController.

LEVEL_GET, LEVEL_XP_NEEDED, LEVEL_PROGRESS and LEVEL_OVERVIEW are bound in Handlers/Level and answered by LevelService under the same names.

UI

Server-driven UI. All are server -> client:

  • UI_COUNTDOWN (CountdownPayload) — RootOverlay renders the timer
  • UI_MESSAGE, UI_HINT — MessageOverlay
  • UI_TOAST — ToasterPortal
  • UI_DIALOG — DialogPortal
  • UI_NOTIFICATION — re-fired by MessageController.ShowNotification
  • UI_MUSIC, UI_MUSIC_STOP — dispatched, not yet consumed

Inventory and hotbar

Client -> server, all bound in Handlers/Inventory, all dispatched from InventoryPortal drag-and-drop except the last two, which come from HotbarPortal: INVENTORY_MOVE_TO_HOTBAR (InventoryMoveToHotbarPayload), HOTBAR_MOVE_TO_INVENTORY (HotbarMoveToInventoryPayload), HOTBAR_SWAP_SLOTS (HotbarSwapSlotsPayload), INVENTORY_SWAP_BAG_SLOTS (InventorySwapBagSlotsPayload), HOTBAR_SELECT, HOTBAR_DESELECT.

Shop and market

Requests bound in Handlers/Shop, Handlers/SeedShop, Handlers/PlayerMarket and Handlers/Products: SHOP_PURCHASE, SHOP_PURCHASE_STOCK, SHOP_PREPARE_ROBUX_PURCHASE, SHOP_SELL_ITEM, SHOP_SELL_ALL, SHOP_EQUIP, SHOP_UNEQUIP, SHOP_GET_INVENTORY, SHOP_REMOVE_ITEM, PLAYER_MARKET_CLAIM, PRODUCTS_GET.

Server notifications: SHOP_INVENTORY, SHOP_REFRESH, ITEM_SHOP_ITEM_ADD (also drives an FTUE step), ITEM_SHOP_ERROR, ITEM_SELL_SUCCESS, ITEM_SELL_ERROR.

Cosmetics: KILL_EFFECT (KillEffectPayload, unreliable, everyone) from CosmeticService.playKillEffect to KillEffectController.

Bases and props

Dispatched from the shared prop classes, which run on both sides: BASE_REMOVE_PROP, BASE_START_PROP_DESTRUCTION (StartPropDestructionPayload), BASE_UPGRADE_PROP, PROP_REMOTE_INPUT (PropRemoteInputPayload), and the developer-product preparation actions SOIL_PREPARE_INSTANT_GROW_PURCHASE, SOIL_PREPARE_STEAL_CROP_PURCHASE, SOIL_PREPARE_STEAL_PRODUCE_PURCHASE. PlacePropPayload, MovePropPayload, SoilAddSeedPayload, AnimalPenAddEggPayload, BasePrepareGrowAllCropsPurchasePayload and BasePrepareHarvestAllCropsPurchasePayload describe the base-editing surface.

Rounds, minigames and voting

Round state is broadcast by BaseGameMode and GameService: ROUND_START, ROUND_END, ROUND_ALIVE_COUNT, GAME_ROUND_INFO (GameInfoRoundPayload) and GAME_ROUND_SUMMARY (GameInfoSummaryPayload) — the last two feed the useRoundInfo hook, the first three feed RoundInfoOverlay and ScoreboardPortal. ROUND_ROLE (RoleRevealPayload) is sent by a game mode to each player as they get a role, and drives the role reveal in RoundInfoOverlay. TEAM_JOIN / TEAM_LEAVE are subscribed by BaseGameMode.

Game selection: MINIGAMES_INIT_CHOOSE_NEXT, MINIGAMES_PLAYER_CAN_CHOOSE, MINIGAMES_NEXT_QUEUED_GAME (bound in Handlers/Minigames), MINIGAMES_CHOOSE_NEXT and MINIGAME_CHOOSE_GAME.

Voting: VOTE_START, VOTE_ENTRIES_UPDATE, VOTE_RESULT_DISPLAY and VOTE_DISABLE are dispatched by VoteService / GameService and consumed by VoteOverlay; VOTE_CAST and VOTE_RESULTS_GET are bound in Handlers/Vote.

Scoreboard: START_SCOREBOARD and UPDATE_SCOREBOARD (ScoreboardPayload, ScoreboardTeam) are consumed by ScoreboardPortal.

Queue

QUEUE_GET, QUEUE_LEAVE, QUEUE_SELECT_MAX and QUEUE_SKIP_VOTE are dispatched by QueueController and bound in Features/Queue/Handler; QUEUE_UPDATE, QUEUE_ALL_STATES, QUEUE_PROMPT_SELECT and QUEUE_REMOVED come back the other way.

Vehicles, mineables, teleports

VEHICLE_SPAWN, VEHICLE_DESPAWN, VEHICLE_LOG_DISTANCE and VEHICLE_GET_ATTACHMENTS are bound in Handlers/Vehicle; VEHICLE_START_CONTROL comes back from VehicleService. MINEABLE_HIT (client -> Features/Mineables/Handler) and MINEABLE_AWARD (server -> MineablesController, which spawns the drop) are the mining loop. TELEPORT_REQUEST and BASE_TELEPORT_REQUEST are dispatched by the TeleportPad watcher and QuickBar.

Gear

GEAR_ACTIVATE ([GearActivatePayload]) and GEAR_SET_SKIN ([GearSetSkinPayload]) are dispatched by GearClient and bound in Features/Gear/Handlers/Gear. The server answers with GEAR_ACTIVATED ([GearActivatedPayload], unreliable, everyone but the owner), GEAR_EFFECT ([GearEffectPayload], unreliable, everyone) and GEAR_STATE ([GearStatePayload], owner only). See the firebit-dev/gearkit package.

Security, monetization, analytics

SECURITY_INIT / SECURITY_PING / SECURITY_PONG are the anti-exploit handshake described in SecurityController; SECURITY_GET_RESPONSES and SECURITY_OFFENSE round out the family. MONETIZATION_FAVORITED_GAME is bound in Handlers/Monetization. ANALYTICS_ERROR and ANALYTICS_EVENT are analytics reports.

NOTE

ADD_MONEY is bound in Handlers/Cheat to a honeypot. It is not part of the protocol — nothing legitimate dispatches it, and anything that does is an exploit attempt.

interface CountdownPayload {
duration: number--

Seconds from the dispatch time until the countdown ends

label: string?--

Heading above the digits. Omitted renders digits only

}

UI_COUNTDOWN. RootOverlay converts duration into an absolute endsAt using the action's serverTime (falling back to Workspace:GetServerTimeNow()), so the timer stays correct regardless of network delay. A duration of zero or less is ignored.

Team rows

The local player's own score

START_SCOREBOARD and UPDATE_SCOREBOARD, consumed by ScoreboardPortal. Both fields are optional so a free-for-all mode can send only localScore and a team mode only teams.

GAME_ROUND_SUMMARY, dispatched by BaseGameMode at round end and read through the useRoundInfo hook. localRewards is the receiving player's own payout, not a table of everyone's.

RoleRevealPayload​

</>
interface RoleRevealPayload {}

ROUND_ROLE, dispatched by a game mode to a player when they get a role, and again when one is promoted mid-round. Drives the role reveal splash in RoundInfoOverlay. The mode owns all the copy; the client uppercases caption and role. Fields are documented on MinigameTypes.RoleReveal, which holds the shape so the client screen can load without red.

Places a prop on a plot. itemRecord identifies the specific inventory record being consumed, so two stacks of the same propItemId stay distinguishable.

Prop being moved

Destination plot

StartPropDestructionPayload​

</>
interface StartPropDestructionPayload {
propId: string--

Prop to start destroying

}

BASE_START_PROP_DESTRUCTION. Begins the timed teardown of a prop; BASE_REMOVE_PROP is what finishes it.

PropRemoteInputPayload​

</>
interface PropRemoteInputPayload {
propId: string--

Prop receiving the call

functionName: string--

Method to invoke on the prop class

args: {any}--

Arguments, forwarded as-is

}

PROP_REMOTE_INPUT — the generic escape hatch for prop interactions. A prop class exposes a named method and the client asks for it by name rather than each prop minting its own action.

WARNING

functionName and args come straight off the wire. The receiving prop class is responsible for validating both against its own allowlist.

HotbarMoveToInventoryPayload​

</>
interface HotbarMoveToInventoryPayload {

Record to move back into the bag

}

HOTBAR_MOVE_TO_INVENTORY, the reverse drag. No slot index — the server finds the record's current slot.

HotbarSwapSlotsPayload​

</>
interface HotbarSwapSlotsPayload {
fromSlotIndex: number--

Slot dragged from

toSlotIndex: number--

Slot dropped onto

}

HOTBAR_SWAP_SLOTS, dispatched when one hotbar slot is dragged onto another. Swaps rather than overwrites, so dropping onto an occupied slot never destroys an item.

InventorySwapBagSlotsPayload​

</>
interface InventorySwapBagSlotsPayload {
fromRecordId: string--

Record dragged from

toRecordId: string--

Record dropped onto

}

INVENTORY_SWAP_BAG_SLOTS, reordering within the bag. Addressed by record id rather than bag index, so a concurrent server-side reorder cannot make the swap land on the wrong items.
