PlayerService

This item only works when running on the server. Server

Owns the player lifecycle: join, profile load, character spawn, respawn and leave.

Join sequence

playerAdded is the spine, and its ordering matters:

  1. Subscribe to PlayerReady before anything can fire it, so the ready signal cannot be missed.
  2. Seed leaderstats with their defaults, then load the profile — a failed load kicks the player rather than letting them play against empty data.
  3. Fire PlayerService.PlayerLoaded, the signal other services should hang their per-player setup off.
  4. Wait for BiomeService.ready so terrain exists before anyone stands on it, then spawn the character — deliberately before waiting for READY, so the client loads into an existing character.
  5. Wait up to LOAD_TIMEOUT (30s) for the client to dispatch READY, kicking on timeout, then push real leaderstat values and broadcast PLAYER_JOINED.
BiomeService is stubbed

Features.Biome was not ported (TODO Layer 12), so the BiomeService used here is a local { ready = true } stub. The chunk-generation wait in step 4 therefore falls through immediately.

Signals

Prefer these over the Players equivalents — they fire with the profile loaded and let listeners clean up before the profile is saved: PlayerService.PlayerLoaded, PlayerService.PlayerRemoving and PlayerService.PlayerReady.

Respawn

Death is handled per character in [PlayerService.initPlayer]: ragdoll the corpse, wait RESPAWN_TIME (2s), then respawn at the original origin. The SpawnOverride player attribute suppresses this entirely, which is how minigames take over spawning without racing this loop.

initPlayer​

</>
PlayerService.initPlayer(
player: Player,--

player to initialise

origin: CFrame--

spawn point, reused for every respawn

) → Model?--

the initial character

Spawns the player's first character and installs the per-character init and respawn behaviour for every subsequent one.

On each CharacterAdded: clears SpawnOverride, waits out a not-yet-parented character, creates the overhead nameplate, applies DEFAULT_WALKSPEED to both the humanoid and the BaseWalkSpeed attribute, and disables the StrafingNoPhysics humanoid state.

Death is handled once per character: ragdoll the corpse into the game container (retained in-world when the character carries KeepRagdollInWorld), wait RESPAWN_TIME, then respawn back at origin. The SpawnOverride attribute is re-checked at three points during that wait, so a minigame can claim respawn control at any moment without racing this loop.

watchForPlayers​

</>
PlayerService.watchForPlayers() → ()

Binds the join and leave handlers, running the join sequence for anyone who arrived before this connected.

On leave: drops the player from the loaded list, flushes their final coin and playtime totals to the leaderboards (coins forced, so a lower value still overwrites), clears their scratch state, fires PlayerService.PlayerRemoving so other services can clean up before the profile is written, then saves and unloads the profile.

Also installs a BindToClose that saves every remaining player, so a server shutdown does not drop the last session's data. Both save paths are gated on ProfileDB.canSaveToDataStore.
