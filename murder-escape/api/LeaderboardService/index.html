LeaderboardService

This item only works when running on the server. Server

Saves player statistic data to ordered datastores in round places, and displays that data on surface GUIs in the lobby. Displays support filtering by global and friends.

Author: Zach Curtis (InfinityDesign)

One OrderedDB instance is created per entry in Shared.Data.Social.LeaderboardData.data, keyed by leaderboard name. Three caches sit in front of those stores and are pushed to clients over LeaderboardData.remote:

  • globalCache — the top GLOBAL_COUNT_TO_DISPLAY (10) entries per leaderboard, refreshed every REFRESH_RATE (60s) and broadcast to all clients.
  • playerCache — the calling player's own value per leaderboard, filled on join.
  • friendsCache — per-player, per-leaderboard values for every friend that has played before (gated on HasPlayedDB), unsorted; the client sorts.

usernameCache fronts UserService:GetUserInfosByUserIdsAsync, which is throttled, and banned/unresolvable users render as [ CONTENT DELETED ].

Inverted feature gate

FeatureFlags.Leaderboards is currently on. Unlike most gated systems, the OFF branch is not a no-op: when the flag is off LeaderboardService.init actively destroys every instance tagged LeaderboardData.DISPLAY_PART_TAG in the place — and keeps destroying newly added ones via GetInstanceAddedSignal — before returning early. Turning the flag off therefore removes the leaderboard models from the running place rather than just leaving them unpopulated.

Overwrites the player's value on the named leaderboard.

By default OrderedDB only accepts a value that beats the stored one; pass forceSet to write it unconditionally. After the write, a debounced LOCAL_UPDATE_DELAY (30s) task replays every leaderboard value back to that client — repeated calls cancel and reschedule the pending push, so a burst of updates results in a single replication.

init​

</>
LeaderboardService.init() → ()

Boots the service and connects data caching.

When FeatureFlags.Leaderboards is off this does the opposite of a no-op: it destroys every instance tagged LeaderboardData.DISPLAY_PART_TAG (the whole model when the tagged part is its PrimaryPart, otherwise just the part), stays subscribed so any later-added tagged instance is destroyed too, and returns without touching the datastores.

With the flag on it connects the OrderedDB instances, primes the per-player and friends caches, kicks off the REFRESH_RATE global/friends refresh loop, binds LeaderboardData.remote for ClientLoaded and GetFriends requests, records every player into HasPlayedDB, and flushes tracked values into the leaderboards when a player leaves.
